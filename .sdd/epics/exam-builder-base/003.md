# T003: Auth — JWT access/refresh + rotation + reuse detection

## Context

Đây là task bảo mật quan trọng nhất trong epic (rủi ro R-2/R-6 mức High trong plan-review) và mọi router từ Phase 2 trở đi đều phụ thuộc vào `require_role` dependency được tạo ở đây. Sai ở task này (ví dụ lưu plaintext refresh token) là lỗ hổng bảo mật nghiêm trọng.

## Description

Implement `TokenServicePort` (application layer) + `JwtTokenService` (infrastructure, implement port) theo AD-2: access token 1 ngày, refresh token 7 ngày, rotation với reuse detection dựa trên bảng `refresh_tokens` (chỉ lưu hash, không lưu plaintext).

## Implementation Steps

1. `app/core/security.py`: hàm `hash_password`/`verify_password` (bcrypt qua `passlib`), hàm `hash_token` (SHA-256) dùng riêng cho refresh token — KHÔNG dùng chung với password hashing (khác mục đích, khác tốc độ cần thiết).
2. `app/application/ports/token_service.py`: interface `TokenServicePort` với `create_token_pair(user_id) -> (access, refresh)`, `rotate(refresh_token) -> (access, refresh) | RotationError`.
3. `app/infrastructure/auth/jwt_service.py`: implement `TokenServicePort`. Access token: JWT ký bằng `JWT_SECRET_KEY`, payload `{sub: user_id, role, exp: now+1day}`. Refresh token: JWT ngẫu nhiên (không cần payload phức tạp) + lưu bản ghi vào `refresh_tokens` (`token_hash`, `family_id` — UUID mới khi login, giữ nguyên khi rotate, `revoked=False`, `expires_at=now+7days`).
4. Logic rotate: given refresh token, hash nó, tìm bản ghi theo hash. Nếu không tìm thấy hoặc `revoked=True` → **revoke toàn bộ `refresh_tokens` cùng `family_id`** (reuse detection), raise `RotationError`. Nếu hợp lệ → set `revoked=True` cho bản ghi cũ, tạo bản ghi mới cùng `family_id`, trả cặp token mới.
5. `app/api/v1/routers/auth.py`: `POST /auth/login` (verify password, gọi `create_token_pair`), `POST /auth/refresh` (gọi `rotate`, trả 401 nếu `RotationError`).
6. `app/api/dependencies.py`: `get_current_user` (decode access token, load user), `require_role(role: str)` — factory trả về dependency raise 403 nếu `current_user.role != role`.

## Acceptance Criteria

- **FR-1 / scenario:** Given thông tin đăng nhập hợp lệ, when `POST /auth/login`, then response có access token (decode được, `exp` ≈ now+24h) và refresh token.
- **FR-1 / scenario:** Given refresh token hợp lệ, when `POST /auth/refresh`, then nhận cặp token mới, và refresh token cũ không dùng lại được nữa.
- **NFR-1 / scenario:** Given một refresh token đã bị rotate (dùng rồi), when gọi lại `POST /auth/refresh` với token đó, then response 401 VÀ toàn bộ refresh token khác cùng family (kể cả token mới nhất chưa hết hạn) bị revoke.

## Tests to Write

- Login thành công trả 2 token hợp lệ.
- Login sai mật khẩu → 401.
- Refresh thành công → token cũ không dùng lại được (test gọi refresh 2 lần liên tiếp với cùng token cũ, lần 2 phải 401).
- Reuse detection: sau khi 1 token bị reuse, token MỚI NHẤT (chưa từng dùng) của cùng family cũng phải bị từ chối khi dùng — xác nhận toàn bộ family bị revoke, không chỉ token bị reuse.
- Test trực tiếp trên DB: query bảng `refresh_tokens`, xác nhận cột `token_hash` không bao giờ chứa giá trị trùng với JWT gốc (không lưu plaintext).
- `require_role("admin")` chặn user thường gọi endpoint admin-only → 403.

## Technical Details

Reuse detection theo family_id là kỹ thuật chuẩn (dùng bởi Auth0, Supabase) — không tự nghĩ ra thuật toán mới, bám theo pattern đã kiểm chứng để giảm rủi ro tự triển khai sai.
