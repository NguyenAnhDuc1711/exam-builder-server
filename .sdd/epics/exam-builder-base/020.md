# T020: Submission + auto-grading + results

## Context

Gộp từ 2 task riêng biệt (submission+grading, results viewing) sau plan-review (RED-1) — cùng entity `Submission`/`Answer`, cùng file router. Đây là task rủi ro cao nhất trong epic: plan-review tìm thấy 2 CRITICAL gap ở đúng luồng này — (1) không có transaction bọc quanh việc ghi Submission+Answer có thể để lại state hỏng nếu lỗi giữa chừng, (2) không có kiểm tra quyền sở hữu khi xem kết quả có thể để lộ dữ liệu của user khác. Cả hai PHẢI được xử lý tường minh trong task này, không phải để ngầm định.

## Description

`POST /exams/{assignment_id}/submit` nhận đáp án, chấm điểm tự động, lưu kết quả trong 1 transaction, enforce single-attempt trả 409 sạch. `GET /submissions/{id}` (user chỉ xem bài của mình — có kiểm tra quyền sở hữu tường minh) và `GET /exams/{id}/submissions` (admin xem toàn bộ, dùng eager loading tránh N+1).

## Implementation Steps

1. `app/application/use_cases/submit_exam.py`: nhận `exam_assignment_id, answers: list[{question_id, selected_option_id}]`. Validate `exam_assignment_id` thuộc về `current_user`. So khớp từng `selected_option_id` với `option.is_correct` của câu hỏi tương ứng, tính `score = số câu đúng / tổng số câu`.
2. **Transaction (CRIT-1):** Bọc TOÀN BỘ việc insert `Submission` + N bản ghi `Answer` trong một transaction duy nhất (`async with session.begin():`). Nếu bất kỳ insert nào raise exception, toàn bộ transaction rollback — không có `Submission` mồ côi không có `Answer` đi kèm.
3. **Double-submit (WARN-2):** Catch `IntegrityError` khi insert `Submission` vi phạm unique constraint (`exam_assignment_id` đã có submission) — convert thành response 409 "Exam already submitted", không để lộ traceback/500 thô.
4. `app/application/use_cases/get_results.py`: hàm `get_submission(submission_id, current_user)` — **(CRIT-2)** nếu `current_user.role != "admin"` VÀ `submission.user_id != current_user.id`, raise 403 TRƯỚC KHI trả bất kỳ dữ liệu nào (không trả partial data rồi mới check).
5. Hàm `list_submissions_for_exam(exam_id)` (admin-only) — **(WARN-4)** dùng `selectinload(Submission.answers)` để load toàn bộ answer liên quan trong 1-2 query thay vì N+1 (1 query submission + N query answer riêng lẻ).
6. `app/api/v1/routers/submissions.py`: `POST /exams/{assignment_id}/submit`, `GET /submissions/{id}`, `GET /exams/{id}/submissions` (`require_role("admin")`).

## Acceptance Criteria

- **FR-6 / scenario:** Given user có đề được giao chưa nộp, when nộp đáp án đầy đủ, then hệ thống chấm điểm, lưu submission, trả điểm + breakdown ngay trong response.
- **FR-6 / scenario (CRIT-1):** Given lỗi xảy ra giữa lúc insert các `Answer` (mô phỏng bằng lỗi injected trong test), when submit, then KHÔNG có `Submission` nào tồn tại trong DB sau đó (rollback toàn bộ, không phải state một phần).
- **FR-6 / scenario (WARN-2):** Given user đã nộp đề đó rồi, when cố nộp lại, then response 409 với message rõ ràng, không phải 500.
- **FR-7 / scenario:** Given user đã nộp bài, when `GET /submissions/{id}` của chính mình, then trả điểm + breakdown đúng/sai từng câu.
- **FR-7 / scenario (CRIT-2):** Given user A đã nộp bài (submission thuộc user A), when user B (không phải admin) gọi `GET /submissions/{id}` với id của user A, then response 403, KHÔNG có dữ liệu điểm/đáp án nào bị trả về.
- **FR-7 / scenario:** Given admin, when `GET /submissions/{id}` bất kỳ, then trả dữ liệu bình thường (admin không bị chặn bởi check CRIT-2).
- **FR-7 / scenario (WARN-4):** Given 1 đề có N submission, when admin `GET /exams/{id}/submissions`, then số lượng SQL query thực thi không tăng tuyến tính theo N (đo bằng SQLAlchemy query counter trong test).

## Interface Contract

**Receives from T012:** `exam_assignment_id` hợp lệ, xác nhận thuộc về `current_user` đang gọi API.
**Produces:** `submission_id`, `score`, breakdown per-question — dữ liệu cuối của toàn bộ luồng nghiệp vụ epic này.

## Technical Details

Race condition khi 2 request submit cùng lúc: application-layer check "đã submit chưa" chỉ là UX nhanh (trả lỗi sớm khi có thể), nhưng nguồn sự thật cuối cùng LUÔN LÀ unique constraint ở DB (từ T002) — code phải catch `IntegrityError` chứ không chỉ dựa vào check trước đó, vì 2 request có thể pass check gần như đồng thời trước khi transaction nào commit.

```python
# app/application/use_cases/submit_exam.py (pseudocode skeleton)
async def submit_exam(assignment_id: int, answers: list[AnswerInput], current_user: User, session: AsyncSession):
    assignment = await get_assignment_or_404(assignment_id, session)
    if assignment.user_id != current_user.id:
        raise HTTPException(403)

    exam = await get_exam_with_questions(assignment.exam_id, session)
    graded_answers, score = grade(exam.questions, answers)  # pure function, no I/O — easy to unit test

    try:
        async with session.begin():  # CRIT-1: single transaction
            submission = Submission(exam_assignment_id=assignment_id, score=score)
            session.add(submission)
            await session.flush()  # get submission.id
            for a in graded_answers:
                session.add(Answer(submission_id=submission.id, **a))
    except IntegrityError:
        raise HTTPException(409, "Exam already submitted")  # WARN-2

    return SubmissionResult(submission_id=submission.id, score=score, breakdown=graded_answers)


async def get_submission(submission_id: int, current_user: User, session: AsyncSession):
    submission = await get_submission_or_404(submission_id, session)
    if current_user.role != "admin" and submission.assignment.user_id != current_user.id:
        raise HTTPException(403)  # CRIT-2 — check BEFORE returning any data
    return submission
```
